# Polish and reach plan (2 Nov 2026)

A full pass over the site after PR #44 merged: design, UX, functionality,
agents (the site as something agents consume, and the repo as something agents
work in) and reach (search, answer engines, generative engines). It came from
four read-only audits of the code at `fcb17d2`; the live site could not be
fetched from the sandbox, so every "deployed" claim below is unverified until
`npm run origin:check` says otherwise.

What this file is not: it does not repeat [ideas.md](../ideas.md),
[seo-backlog.md](seo-backlog.md) or [review-response.md](review-response.md).
Where an item there is still the right next move it is named and ranked, not
rewritten. Items the owner has already declined (FAQ filler, an SEO dashboard,
translations, a tool dashboard on `/`, long landing pages) stay declined.

Delete each item as it ships. §8 lists the decisions only the owner can make;
§7 is the order.

## 1. Principles for this pass

1. **Finish or delete.** Several half-built things sit in the tree (palette,
   kit, service worker, the vitals beacon, Flash Cricket). Each one either ships
   this pass or goes, so the code and the docs stop describing two sites.
2. **Ship fewer, larger things** (AGENTS.md, *The bar*). The two product bets
   in this plan are the Webhook Inspector and the Poker Trainer; everything
   else is polish, plumbing or correctness.
3. **Every new invariant gets an assertion** in `security-smoke.mjs` or
   `tools-hub-smoke.mjs`, mutation-tested.
4. **No new secrets on the host.** The one new credential (a Cloudflare purge
   token) lives in GitHub Actions, never in the container.

## 2. Reach: search, answer engines, generative engines

### 2A. One entity, everywhere (markup)

The Person on `/` has no `@id`, so every `author` and `publisher` on the other
48 pages is a bare name that nothing can merge back into it. This is the
cheapest real SEO/GEO gain left in the markup.

- Give the Person a stable `@id` (`https://apanjwani0.com/#person`) and the
  WebSite `#website` in `src/lib/jsonld.ts`; reference both by `@id` from
  `blogPostingJsonLd`, `webAppJsonLd` and `webSiteJsonLd`.
- Add `alternateName: site.handle` and a short `knowsAbout` list (payments,
  webhooks, TLS, DNS, cron) to the Person; wrap the home Person in a
  `ProfilePage`. This is the markup half of the "bare name does not find the
  site" problem (seo-backlog.md).
- `WebApplication` gets `image` (the share card already exists for every live
  tool and game) and `isPartOf: {@id: '#website'}`.
- A learnings article that embeds a tool gets `about: {WebApplication, url}`;
  the page already computes the relation (`learningsAboutEmbed`). Add
  `mainEntityOfPage`, `inLanguage` and `wordCount` while there.
- Open Graph on articles: `article:author` becomes the home URL (it is the site
  name string today), and `article:modified_time` and `article:tag` are
  emitted.
- Drop `<meta name="keywords">` and the JSON-LD `keywords` (decision D7,
  review-response.md). The lists stay as palette synonyms.

### 2B. Freshness that is true

- Add an optional `updated` field to `Learning` (and later to tools and
  games). Emit `dateModified` in JSON-LD and `<lastmod>` in the sitemap only
  from a real date. Today `lastmod` is set on 6 of 49 URLs and absent on the
  rest; Google discounts a `lastmod` it cannot trust, so an honest partial beats
  a stamped-everywhere one.
- `Last-Modified`/`ETag` on `/sitemap.xml`, `/llms.txt` and `/feed.xml` in
  the middleware, derived from the newest `updated`.

### 2C. IndexNow and Bing

Google is not an IndexNow participant, but Bing, Yandex, Seznam and Naver are,
and ChatGPT's web search leans on Bing's index. This is the single "AGO/GEO"
plumbing item with a known payoff.

- `public/<key>.txt` holding the key (it is public by design, so it ships in
  git), and `scripts/indexnow.mjs` that POSTs a URL list to
  `api.indexnow.org` with `host`, `key`, `keyLocation`.
- A deploy step that submits only what changed: diff this deploy's sitemap
  against the previous one (kept as a workflow artifact) plus any URL whose
  `updated` moved. Never resubmit the whole site on every deploy.
- Owner action: verify the site in Bing Webmaster Tools (the IndexNow key
  doubles as proof), and import from Search Console.

### 2D. A feed

There is no RSS or Atom feed and no `<link rel="alternate">`. With two
articles it is cheap, and feed readers, Bing and polling agents all use one.
`src/pages/feed.xml.ts` reuses `indexablePaths` and the learnings fields;
Head.astro gets the discovery link. Articles only; tools are not feed items.

## 3. Agents

### 3A. The site as something agents call

Three server tools (Chainsaw, DNS Sightline, Link Peek) are already
unauthenticated JSON `GET`s with bounded limiters, which is the right shape.
What is missing is a contract and a front door.

- **An API description.** `GET /openapi.json` (outside `/api/`, which
  `robots.txt` disallows) describing the three routes, their query shapes,
  the `{ok:false,error}` 429 with `Retry-After`, and the limits. Generated from
  one TypeScript source so it cannot drift from the handlers.
- **An MCP server**, stateless Streamable HTTP at `POST /api/mcp`, exposing
  `inspect_tls`, `inspect_dns`, `peek_link` and `create_webhook_bin` /
  `list_webhook_requests`. It wraps the library functions (`csInspect`, the
  `sg*` lookups, `lpFetchPage`, the webhook store), not the HTTP routes, and
  spends the **same** limiter buckets, per-client first and then global, so an
  agent cannot starve a human. No auth, no API keys, no IP allowlist, no
  user-agent privilege (AGENTS.md). Body capped. This is the one new thing in
  the plan that clears the tool bar outright: a URL other software talks to.
- `/.well-known/security.txt` (contact, expires, canonical). `/.well-known/`
  also hosts the MCP descriptor if one is wanted.
- CORS stays off on the tool routes unless a browser client is a goal; the
  webhook capture route keeps its `*`.
- Assertions: limiter pairing on the new route, the OpenAPI document matching
  the handlers' accepted parameters, and `robots.txt` not disallowing the
  descriptor path.

## 4. Functionality

### 4A. Webhook Inspector: the one product bet

It already clears every line of the bar. Against webhook.site, webhook.cool
and Hookdeck's console it is missing the things a stranger would bookmark for:

1. **Live arrival.** It polls every 2 s and stops when the tab is hidden. An
   SSE route (`/api/hook/:bin/stream`) replaces the poll, and the tab title
   carries an unread count. Bound it: one stream per bin per client, a
   connection cap, a hard idle close.
2. **Replay and copy.** "Copy as curl" of the *captured* request (today the
   curl button emits a fixed sample), and "Resend to URL" through the same
   SSRF guard Link Peek uses.
3. **A configurable response.** Body, `Content-Type` and headers per bin, not
   just `?status` and `?delay`; redirects with `Location` and 1xx allowed.
   Bounded per bin and counted in the global byte budget.
4. **Bins that survive a deploy.** Flush to `data/` the way the daily boards
   do, with the same 6 h idle TTL and re-validation on load. That turns "state
   outlives the tab" from mostly true into true.
5. **Export by URL**: `GET /api/hook/:bin/requests?format=ndjson`, so CI can
   pull a run.
6. **More signature schemes**: Standard Webhooks (Svix), Twilio, Discord
   (ed25519), Paddle, Mailgun, SendGrid, each in `signature.ts` and each
   asserted against a real captured fixture. Keep the raw body bytes for the
   HMAC, not the decoded text.
7. Smaller: filter captured requests, a per-bin rate bucket under the per-IP
   one, rotate a bin id.

`/terms` updates in the same commit as item 4 (retention changes).

### 4A2. Poker Trainer: the second product bet

The owner played the drill (2 Nov 2026): good for understanding, but a few
numbers were not explained properly, the spots all feel alike, and it wants
multiple players, bet-size variation and more realistic situations. The code
agrees. Every drill is pot 100, a bet of 33, 50, 66 or 100, one opponent
holding a random *preflop* preset range that never narrows after betting, no
positions, no stacks, and a raise verdict that is a hidden `equity >= 0.68`
with no explanation anywhere on the page.

**Scenario engine** (`engine/scenarios.ts`, pure, seeded, exact): seven
situation templates, each a story whose pot is derived from the chips that
went in, so every number on the felt has a line that produced it:

1. Single raised pot, hero in position (caller vs an opener's c-bet).
2. Single raised pot, hero defended the big blind, out of position.
3. Three-bet pot, shallow stacks, where a bet is often a shove.
4. Multiway: two opponents, one bets, one calls, hero last to act. Exact
   three-way equity by enumerating opponent-hand pairs, so turn and river
   only; a flop spot is rolled forward until it is affordable.
5. Facing a shove, from half-pot to a 2.5× overbet; raising is impossible.
6. Hero bet, got raised: the chips hero already put in belong to the pot.
7. River, from half-pot to a 2× overbet, where the bet size says what they
   hold.

Bet sizes run from a third of the pot to a 2.5× overbet, and **a size narrows
the range** by one stated rule each (a small bet is the whole range; a medium
bet is a pair or a strong draw; a large bet is top pair or better; an overbet
or shove is polarised). Each rule is one plain sentence the page prints.

**The decision is a model with every number named**, not a threshold. The
call is graded on break-even equity against exact equity, as now. The raise is
modelled: the opponent continues against a 3× raise with the strong part of
the range they bet with and folds the rest, and the page prints the raise EV
line with the fold share, the calling share, hero's equity against the
callers and the 5%-of-pot margin a raise must clear, with the assumption
stated (nothing after this street is modelled). Multiway and all-in spots
offer no raise and say why.

**Numbers explained.** The ledger names every quantity once and uses the
same name everywhere: pot before their bet, their bet, pot now, your call,
pot after your call, break-even equity, pot odds as "X to 1", your equity
(wins plus half of ties over N runouts, with the counts shown), EV of calling,
share of their hands you are ahead of, and the raise line. Each card shows
the formula with the real numbers substituted and a one-sentence definition.

**Also:** positions and stacks on the felt (seats already exist), the line of
play printed above the board, a situation filter (all, heads-up, multiway,
shoves, three-bet pots), per-situation accuracy kept locally (bounded), and
permalinks that encode template plus seed so a spot is reproducible; old
`?spot=` links keep working. The `seoContent` FAQ block on the game is
emptied per the rule (§2H) and the description stops promising "GTO".
Assertions in `scripts/poker-check.mjs`: pot arithmetic reconciles with the
line for every template over hundreds of seeds, the range filters keep and
drop what their sentences say, three-way equities sum to one, the judge's
reasons contain every number it used, and decode(encode(spot)) round-trips.

Shipping in the first PR of this plan, together with the docs streamlining
and a measured performance pass.

## 5. Design and UX

palettes, self-hosted metric-matched fonts with no swap shift, the one-card
anatomy with the whole card as a link, the skip link and `main` focus

### 5A. A way to reach the owner

Home offers GitHub and LinkedIn; there is no email, no résumé, and no
"about" beyond the footer bio, which home does not render. Add optional
`site.social.email` (a mailto) and `site.resumeUrl`, shown as a third hero

**Owner decision**: whether to publish an address and a CV at all.

### 5B. Touch targets outside the control kit

Nav, footer and breadcrumb links are text-only at label size, about 15–18 px
tall on a phone; the 44 px rule exists only in `controls.css`. A
`--target-min` token and a `@media (pointer: coarse)` block giving those
links `min-height` and `padding-block`.

### 5C. Forced colours and print

Nothing in `src` handles `forced-colors`, `prefers-contrast` or `print`. One
block in `shared.css`: in forced colours, a `CanvasText` outline on
`:focus-visible` and a `CanvasText` border on card, field and control; in
print, hide nav, footer, starfield, sky and skeletons, body black on white. An
article printed today carries the sky.

### 5D. Token hygiene

- Literal spacing in `404.astro`, `Breadcrumbs.astro`, `Footer.astro`,
  `Nav.astro`, `RelatedLinks.astro` (about 11 `rem` values) and literal
  durations in `shared.css` move to `--space-*`, `--motion-*`, `--ease-*`.
  Then a smoke assertion: no literal `rem`/`ms` in a component `<style>`.
- Add `--color-warning` and `--color-warning-soft` to both palettes, through
  the contrast sweep; `poker-trainer.css` already reads the token and gets
  its fallback today.
- `--z-sky`, `--z-content`, `--z-nav`, `--z-skip` replace the magic numbers.
- `--focus-ring` and `--focus-offset`; Footer and RelatedLinks stop
  re-declaring their own outline.
- `--text-title` and `--text-lg` become clamps like their neighbours, so the
  h1 scales between 375 px and a wide desktop.

### 5E. Accessibility inside tools

- The `:not(:defined)` skeleton is a silent grey box: give it
  `content: "Loading the tool…"` in muted small text, no animation.
- Every result or status node gets `role="status"`; errors `role="alert"`,
  which the kit's `status-line` should do by default. AudioTranscriber and
  Draftboard have no live region at all.
- Raw `<textarea>`, `<select>` and `<input>` without a label in Flowmap,
  Token Bench, Cron Whisperer and others. Fix them, then a lint in
  `tools-hub-smoke.mjs`: every control has `aria-label`, `aria-labelledby`
  or a matching `<label for>`.
- `data-tone` status conveys meaning by colour alone; prefix a word
  ("Error:", "Done:") through `::before`.
